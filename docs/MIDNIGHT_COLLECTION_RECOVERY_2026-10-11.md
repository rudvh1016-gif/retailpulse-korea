사용자 요청: “면세 환율부터 항공편 또 열두시 넘어가니까 바로 안 떠. 미리미리 수집할 수 있게 조치를 해놔 안전장치를 여러번 해놔서 절대 누락 안 되게 해놔.” 범위는 별도 브랜치 구현·검증·draft PR이다. 에이전트 병합·배포, 수동 생산 수집/DB 쓰기는 승인되지 않았다. 시작 main은 `70ec17577c7ff9fb4b4beffae21c647a9e05532e`이다. PR330의 디자인 변경은 이 수정에 포함하지 않는다.

- 공개 GET 확인 2026-10-11 00:09 KST: 환율 API 오늘 날짜는 10/11이지만 저장값은 10/10, USD 1339.20이다. 마지막 성공 10/10 23:52:54.577 KST, 다음 가능 시각 10/11 00:52:54.577 KST였다. [기존 실행 38061333540](https://github.com/rudvh1016-gif/retailpulse-korea/actions/runs/38061333540)의 성공 뒤 시간당 due guard가 날짜 전환에도 적용되었다. [00:07 실행 38062328595](https://github.com/rudvh1016-gif/retailpulse-korea/actions/runs/38062328595)은 `SKIPPED_NOT_DUE`, providerRequests=0이었다.
- 00:14 KST 공식 신라 홈페이지의 정상 GET은 HTTP200, 실제 `.exchange .sum`에 `$1=1,339.20원`, 문맥은 “오늘의 환율”이었다. 명시 날짜가 없는 CURRENT_WIDGET이므로 기존 승인 정책대로 확인 시각의 날짜에만 적용하며 내일 값으로 추정하지 않는다. 원천이 새 환율을 공개하지 않았다고 단정하지 않는다.
- 같은 시각 공개 오늘 항공편 API는 **573편**, `OFFICIAL_DEPARTURE_SCHEDULE`, 마지막 변경 수집 10/10 09:42 KST였다. 내일 10/12은 561편이었다. 실제 390px 브라우저에서 전체 573편·T2 269편과 “오늘 운항 기록 수집 대기 · 공식 출발 예정표 기준”을 확인했다. T2 게이트 미확인 269편/100%는 구역 수치 계산 불가이며 데이터 0편과 다르다. 콘솔 오류·수평 넘침은 없었다.
- 오늘 실제 `airport_flights` 관측은 coverage witness에서 MISSING_TODAY였으나 witness는 보유 공식 예정표를 검사하지 않는다. 이 상태로 전체 항공편 API가 비었다고 보고하면 안 된다. 조사 당시 오늘 00:07 명목 early-A1는 실제 Actions 실행 목록에 아직 없었다. GitHub schedule 지연 가능성을 확인한 것이며 원천 NOT_YET_PUBLISHED가 발생했다는 생산 증거는 아직 없다.
- 00:22:51 KST [후속 실행 38063335339](https://github.com/rudvh1016-gif/retailpulse-korea/actions/runs/38063335339)도 환율 SKIPPED_NOT_DUE/providerRequests0, 00:22:53 coverage MISSING_TODAY가 유지된 것으로 부모 작업에서 확인했다. 이 기록을 새 수정의 생산 실행 결과로 취급하지 않는다.

## 기존 경로의 보강

1. 환율 SQL claim: 전날 **SUCCESS**가 남아 있고 오늘 daily 행이 없을 때 새 KST 날짜의 첫 확인을 허용한다. 오늘 날짜 attempt로 즉시 기록하므로 같은 날 반복 예외가 생기지 않는다. 이미 명시 날짜의 내일 값을 보유하면 불필요한 자정 예외 없이 원래 확인 시각을 보존한다. BLOCKED·실행 중 lease·전날 미완료/오류의 기존 제한을 무시하지 않는다.
2. 오늘 환율이 없는 자정 첫 한 시간은 15분 durable due 간격이다. 일시 실패나 명시 내일만 나온 응답도 이 간격을 따른다. 오늘 값이 생기거나 첫 시간이 지나면 1시간, 계약/403/406 등 BLOCKED는 24시간이다. HTTP 전에 예산을 기록하고 lease 만료만으로 간격을 초기화하지 않는다. 같은 의미 값은 canonical 재쓰기 0회이며 실패로 이전 날짜/확인 시각을 갱신하지 않는다.
3. A1의 완전한 성공 스캔이 NOT_YET_PUBLISHED이면 기술 오류 재시도와 별도 verdict를 기록한다. 검증 가능한 자기 실행의 targetDate·실제 요청 수·마지막 상태만 읽으며 같은 KST 날짜의 00:00–02:59 안에서만 자격을 준다. **기존 retry_1/retry_2 두 작업**을 각각 최소 5분 간격으로 재사용한다. 해당 경우 A1만 실행해 A2 반복을 피한다. 인증/스키마/저장/429/불명 로그는 공개 대기 판정이 아니다.
4. 이미 저장하는 A1 미래 일정과 A3 예정표, 일별 cache, 날짜 전환 API 검증, last-good 유지, 오늘 성공 스캔 중복 방지, 원자적 rolling request reservation을 재사용한다. 새 반복 cron·Worker 수집·provider endpoint·유료 경로·schema migration은 추가하지 않았다.

## 비용·검증의 한계

- 환율의 이전 최대 24요청/일 추정은 이 승인된 자정 회복 구간에 그대로 적용할 수 없다. INTERNAL_ESTIMATE: 자정 첫 시간 최대 4요청, 나머지 시간당 1요청으로 KST 일 최대 27요청; rolling 24시간 보수적 상한 28요청. 실제 기존 15분 스케줄과 지연은 이보다 적을 수 있다. 한 claim당 provider 요청은 여전히 1회이다. 운영 claim/완료 최대 56행/rolling 24h, 하루 달력별 행과 CURRENT는 semantic changed-only이며 PK 인덱스 비용·계정 전체 무료 사용량은 미측정이다. 방문자 수가 provider 호출을 늘리지 않는다.
- A1는 기존 3×125+일일125=500 계획, 원자적 rolling 24h 500회 제한이 그대로다. 이전 수집/미완료 reservation이 있으면 실제로는 그보다 적게 허용하며 공개 대기 check도 예산 부족 시 요청 0회로 중단한다. 추가 작업은 최대 두 번의 5분 대기이며 GitHub 실제 시작 시각은 예약 시각과 다를 수 있다.
- 외부 공개 시점·스케줄 지연·네트워크·무료 예산 때문에 “어떤 상황에도 누락 없음”이나 게이트 공개 전 확정 수치를 보장할 수 없다. 마지막 정상 날짜와 예정/실제/미확인 구분을 유지하는 것이 필수다. 생산 활성/공개 성공은 사용자 병합·자동 배포 후 실제 수집과 API를 다시 확인해야 한다.

검증 명령·커밋·PR·CI 결과는 PR 본문에서 최신 상태로 기록한다. UI Lock 61개 파일과 cron fixture는 변경하지 않는다. 새로운 자정 예산 예외는 본 문서가 기존 DUTY_FREE_EXCHANGE_AUTO_REFRESH.md 및 DUTY_FREE_TODAY_KST_2026-10-09.md의 과거 시간당 정책/비용 추정보다 우선한다.
