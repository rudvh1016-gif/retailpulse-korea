## 핵심 질문 8개

아래 등급은 기존 구조의 측정 가능 범위다. 실제 사용자 수나 수신 완료를 뜻하지 않는다. 모두 기존 동의자·분석이 차단되지 않은 기기에 한정되며, GA4 보고서를 이번 세션에서 직접 열람하지 못했다.

| 질문 | 판정 | 기존 근거와 한계 |
|---|---|---|
| 1. 첫 화면을 실제로 보는 사람이 있는가? | PARTIALLY_MEASURABLE | 홈에 있는 `onboarding_started`, `onboarding_completed`, `briefing_viewed`가 수신되면 일부 홈 이용의 간접 근거다. 공개 요약만 본 사람과 전체 홈 조회수는 기록하지 않는다. |
| 2. 홍대·명동·성수 상세에 들어가는가? | NOT_MEASURABLE | 상세 링크·페이지 이동 이벤트가 없다. `location_selected`는 설정 선택이며, `briefing_viewed.location`은 개인 브리핑 지역이다. 상세 진입으로 해석하지 않는다. |
| 3. 인천공항 상세를 보는가? | NOT_MEASURABLE | 공항 상세 페이지 조회 이벤트가 없다. `location=airport` 브리핑 조회는 공항 상세 조회가 아니다. |
| 4. TODAY·TOMORROW·7DAYS 중 무엇을 보는가? | PARTIALLY_MEASURABLE | 개인 브리핑의 `briefing_viewed.day`는 `yesterday/today/tomorrow`를 구분한다. 공개 날짜 메뉴와 7DAYS 이용은 기록하지 않는다. 기존 보고서에 day 측정기준이 없으면 날짜별 분해도 확인할 수 없다. |
| 5. 같은 사용자가 다시 방문하는가? | PARTIALLY_MEASURABLE | 기존 GA4의 동의 기기 기준 재방문과 반복 이벤트를 참고할 수 있다. 실제 동일인·기기 간 재방문을 증명하지 않으며 쿠키 삭제·분석 차단·공개 요약만 보는 재방문은 놓친다. 보고서 수신·표시 가능 여부는 별도 확인이 필요하다. |
| 6. 개인 브리핑을 설정하거나 사용하는가? | MEASURABLE | `onboarding_completed`, `briefing_viewed`. 설정 완료와 조회를 분리한다. 같은 사람이 지역·날짜를 바꾼 이벤트를 새로운 사람으로 세지 않는다. 접힌 브리핑은 조회 이벤트를 만들지 않는다. |
| 7. 도움이 됐다는 피드백이 있는가? | MEASURABLE | `briefing_helpful_yes/no`. 응답자만의 결과이며 무응답은 부정 의견이 아니다. |
| 8. 실제 업무에 사용했다는 반응이 있는가? | PARTIALLY_MEASURABLE | `briefing_used_for_work_yes/no`는 매장 영업관리자 역할에만 노출된다. 자기 보고이며 업무 성과의 검증이 아니다. 관광통역안내사 등 다른 역할의 업무 사용은 이 버튼으로 확인할 수 없다. |

## 기존 analytics·feedback 사용 방법

- 근거: `lib/personal-analytics.ts`, `app/personal-home.tsx`, `app/personal-preferences.ts`, `docs/PERSONAL_BRIEFING_OPERATIONS.md`.
- 공개 페이지 자동 조회는 `send_page_view:false`; `page_location`은 origin으로 제한된다. 상세 경로나 이동 경로를 역산하지 않는다.
- 현재 Production 배포 로그에서 GA4 활성화 플래그와 실제 측정 ID 주입은 확인했다. 실제 GA4 수신, 기존 맞춤 측정기준 등록 상태, 현재 관리 화면 설정은 직접 확인하지 못했다. 코드 존재만으로 수신 성공이라고 쓰지 않는다.
- 기본 이용 통계 동의는 꺼져 있다. 동의하지 않으면 GA 스크립트·이벤트 전송을 시작하지 않는다. 철회는 이후 전송을 중단하며 과거 전송분 삭제가 아니다.
- 피드백은 기기 내 날짜·역할·지역·터미널·질문별 중복을 막고 최근 100개만 보관한다. 미동의 피드백은 기기에만 남아 중앙 집계할 수 없다.
- 운영자는 기존 GA4 이벤트 보고서에서 위 이벤트 수신을 먼저 확인하고, 시험 기간의 이벤트 수·사용자 수와 표시 가능한 기존 역할/지역/day 분해만 기록한다. GA4 속성의 시간대와 KST 범위 차이를 확인하되 설정을 임의 변경하지 않는다.
- 맞춤 측정기준이 이미 없으면 새로 등록하거나 새 이벤트를 넣지 않고, 해당 분해를 확인 불가로 남긴다. 사용자 식별자·이름·이메일·회사·근무 일정은 시험 문서에 수집하지 않는다.
- 실제 수신이 확인되지 않거나 이벤트가 0이면 동의·차단·연결·유입 여부를 구분한다. 0을 곧바로 수요 없음으로 판정하지 않는다. 이번 점검의 조작을 실제 사용자 반응으로 세지 않는다.

## 과거 자료는 어떻게 쌓이는가

- `lib/collector.ts`는 서울 관측을 `source_id + area + observed_at`별로 저장한다. 새 관측시각은 새 행이고 같은 관측의 변경 없는 재수집은 덮어쓰지 않는다. 현재 운영 정리 함수는 서울 관측 행을 삭제하지 않는다.
- 최근 정상 수집 실행 `34692160429`에서 `seoul_realtime` SUCCESS와 changedRows 42를 확인했다. 이는 인구·공식 예보 등 해당 수집 묶음의 변경 건수이며, 인구 관측 42점이라는 뜻이 아니다. 미래 예약 실행 성공을 보장하지 않는다.
- `lib/period-comparison.ts`는 7일/28일 전의 **동일 KST 시각(분·초 포함)**, 같은 지역·출처·스키마·VALID 자료만 비교한다. 28일은 4주 평균이 아니다.
- 2026-09-12 공개 홈에서 홍대 관측 `20:20`과 `2026-09-05 20:20`의 전주 범위 비교를 실제 확인했다. 이후 관측 `20:25`에 대응하는 과거 시각이 없으면 다시 비교자료 없음이 될 수 있다. 이것은 엄격한 동일 시각 조건에 따른 정상 동작이다.
- 따라서 정상 수집과 동일 시각·동일 정의의 행이 모두 존재하면 비교는 자연스럽게 가능해진다. 약 15분 수집과 공급자 관측시각 차이 때문에 모든 분의 비교가 채워지는 것은 아니다. 28일 비교는 28일 전 대응 행이 필요하며, 2주 시험 종료일까지 모든 지역·시각이 채워진다고 약속하지 않는다. 근사 시각·보간·평균으로 채우지 않는다.

### 이번에 발견한 실제 BUG: 관측 이력 반환 누락

- 수집된 과거 행이 있어도 `/api/live/summary`가 최신 관측만 반환하고 `observedSeries`를 제공하지 않았다. 기존 차트가 과거 관측을 받을 수 없으므로 시간만 기다려서는 여러 점으로 늘어나지 않는다.
- 기존 SQLite 기반 요약 검사에 두 관측 행을 넣어 반환 누락을 재현했다. 단순 데이터 부족과 구분되는 조회 버그다.
- 최소 수정: 같은 요약 응답·캐시·D1 batch에서 오늘 최근 6시간, 지역당 최대 73개 원본 관측을 반환한다. 기존 인덱스를 사용하고 원본 상·하한·시각을 보존한다. 다른 출처·스키마·측정 구역, 무효·미래 자료를 제외한다. 다른 날짜 화면에 오늘 관측을 넣지 않는다.
- 브라우저 요청과 D1 왕복은 기존 1회다. 캐시 miss에서 제한된 관측 읽기는 추가되며, 이를 비용 변화 없음이라고 부르지 않는다. 세 지역의 반환 상한은 219행이다. 인덱스 검색·6시간 범위·행 상한·한 번의 D1 왕복을 SQLite 검사로 확인한다.
- 차트의 결측 단절 규칙은 바꾸지 않는다. 15분 간격으로 수집된 점 사이에 없는 5분 관측을 만들어 연결하지 않는다. 과거 화면·새 차트·새 공급원·새 API 경로·스키마·수집 일정은 추가하지 않는다.

## 개발 중단과 예외

화면과 측정 조건을 고정해야 실제 사용 반응을 비교할 수 있다. 시험 중 선호에 따른 디자인 변경이나 기능 추가로 조건을 계속 바꾸지 않는다.

- **P0 즉시 수정:** 잘못된 숫자, 관측/예측 혼동, 잘못된 날짜·지역·터미널, 페이지 미개방, 핵심 API 실패, 모바일 핵심 내용 사용 불가.
- **P1 즉시 수정:** 중요한 버튼 동작 오류, 실제 비교자료의 미표시, 심각한 글자 잘림, 이번처럼 이미 저장된 관측의 조회 누락.
- 금지: 더 예뻐 보일 것 같다는 이유, 카드 위치·색상 취향, 새 차트·지도·지역·데이터·사업기능. 새 GA/외부 분석·쿠키·식별 강화·개인정보·runtime LLM을 추가하지 않는다.
- 수정은 재현 근거·최소 변경·관련 검사·기존 승인/CI/배포 절차를 따른다. 오류가 없으면 PR·재배포를 만들지 않는다. 치명적인 측정 공백으로 시험 자체가 성립하지 않으면 추가 측정 필요로 보고하고 구현은 멈춘다.

## 종료 후 판단

- 9월 26일 기존 보고서·피드백의 관측 가능한 범위만으로 판단한다. 자동 후속 점검을 예약한 것은 아니다.
- 자발적인 반복 사용과 도움이 됨/업무 사용 반응이 있으면 어떤 역할·상황에서 유용했는지 기존 근거 안에서 정리한다. 이벤트 횟수와 실제 사람 수를 혼동하지 않는다.
- 클릭이나 칭찬만 있고 재사용·업무 사용 근거가 부족하면 성공으로 확정하지 않는다. 미측정 상세 진입·7DAYS 이용을 추정해 채우지 않는다.
