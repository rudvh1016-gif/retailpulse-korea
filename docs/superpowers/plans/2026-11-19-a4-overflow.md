# Future A4 overflow: isolated readiness and rollout plan

Goal: one destination per future A4 capture, same provider work, untouched legacy airport rows and shared control plane. This patch is the disconnected readiness slice; it does not bind or route production.

1. Add tests for explicit, schema-ready single write destination, cutover/future guard, wrong source/terminal rejection, whole-generation selection, and degraded fallback. Run red.
2. Implement bounded pure routing and per-terminal generation selection. Supply standalone A4-only schema for isolated staging, never as a primary D1 migration. Run fixtures and related existing recovery/collector tests.
3. Before activation: integrate primary and retry writers, manual imports/recovery procedures, both public readers and operational readers. Prove shared state identical and preserve atomic A4 health CAS. Exercise the full Worker and REST paths in staging before considering a production flip.

## Design and staging details

Writers: collect-realtime-cycle.yml invokes collect-production.ts through collect-attempt.yml for both normal and retry. Both collector functions currently use the same env.DB for observation rows and for source health and collector run evidence. Manual import-oneshot.ts and scheduler/diagnostic paths also need explicit destination review. No extra provider requests and no fallback write on ambiguous storage error; provider-connect retry policy must not see a shard storage error as a provider failure. Keep the primary DB binding and first configured REST database unchanged; add a distinct optional binding and explicit distinct REST target only after staging.

Readers: /api/live/summary and /api/airport/facility-operations select the latest independently for T1 and T2. A shard needs a separate bounded query, not a mixed primary-statement batch; choose one generation per terminal, preserving window/freshness and partial-data semantics. Source identity, observed and retrieved times, and fallback status must survive composition. Main DB remains historical. data-coverage.ts, operational-evidence.ts, operational-congestion-recheck.ts and production read-budget/storage diagnostics need deliberate shard-aware semantics. The current markA4Healthy CAS jointly asserts latest A4 data and primary health/run state in one statement. Do not weaken it or let a stale primary sample confer HEALTHY after shard activation. Production remains off until an equivalently safe design is proven, or a separately reviewed explicit disabled-automation behavior is accepted.

Read rollout first with currently empty staged shard, then isolated fixtures for empty, stale, unavailable, newer, equal, malformed, partial, duplicate, T1-only, T2-only, and rollback cases. Check the public reply and witness coverage, never fabricate live data. For rollback stop shard writes, leave merge reads on, wait until natural primary writes have caught up for both terminals and verified freshness, then turn shard reads off. A failed or unavailable shard is surfaced as degraded. Test stale-fallback behavior before activation; do not restart collectors or backfill for verification.

Sizing: 20 typical changed rows/cycle x 96 cycles/day = ~1,920 rows/day; conservatively 4 billed writes per inserted row = 7,680/day, shifted not added in normal operation; real traffic, retries and shared status writes may differ. Per-account free daily write/read quotas are unchanged. Measure actual bytes/day, read amplification, index costs, and size on staged receipts; two databases are separate 500 MB limits, not one dynamic 1 GB DB. Adding the shard does not recover bytes on primary. Track remaining primary growth from all other collectors separately; no current deletion, transfer, or archival.

## Required publication contract for operational parity (not implemented here)

Atomically insert a full immutable per-terminal capture and manifest (content digest, row count, generation ID and canonical observed/retrieved times) in overflow. After verified commit, atomically publish a bounded, monotonic per-terminal pointer with the associated run/health in primary. A timeout retries database work with the same captured data and identity, never the source fetch; ambiguous commits require explicit readback. An orphaned generation is invisible. Readers query the exact published key and validate manifest integrity; failed reads/digest/shape are degraded. Incident recheck does shard verification first, then atomically compares the primary pointer unchanged together with the original run/health/state guards. Immutability is essential to that proof and staging must test both interleavings (pointer advance before CAS, or newer unpublished data after CAS). Leave room for existing primary shared writes and pointer metadata. The proof-of-concept SQL schema here is not by itself the final immutable manifest schema and cannot be used for a live integration.

Transport caps: REST executes at most 50 statements and runD1Batches chunks 40; T2 can normalize up to 60 rows. Use one bounded manifest/payload row, or proven bounded grouped writes with visibility only on complete publication. A successful chunk is not proof of a complete generation. Staging must inject partial success, missing generation, 403, 507, stale fallback, and concurrent newer pointer publication. Production writer metrics currently snapshot only the primary REST client; add separate primary/overflow measurements or an explicit aggregate. Future binding lookup should resolve named bindings, not re-order the existing first element.

## Local reference adapter

The second local slice, `lib/a4-overflow-publication.ts`, stores an entire terminal capture as one immutable payload row, at most 60 rows/48 KiB. It verifies exact bytes, SHA-256, row count, source, terminal, observation time and unique zones before publication/read. Tests use two independent SQLite databases and injected interleavings; actual D1 durability, freshness, retention lifecycle, transaction composition with production health/run writes, and max binding/body overhead are still staging gates. Fixture immutability forbids deletes; before deployment choose and verify an explicit retention lifecycle that can never remove the currently published or reasonably in-flight generation. The older routing-only SQL fixture is not the manifest schema used by this adapter. No deployment configuration, network authorization or live code is changed.

The local D1-compatible adapter opens two explicitly distinct bindings. The Miniflare fixture exercises true local D1 `batch()` rollback of a pointer update when a subsequently batched evidence insert fails. Its synthetic evidence is not production `collector_runs` or `source_health`. Next wire those existing SQL helpers as bounded prepared statements with stable run identities and exact pointer predicates, preserving existing behavior on non-A4/default OFF; migrate only staged resources, and verify REST transport batch rollback separately (the local test covers Worker D1 runtime, not remote REST). Then integrate read-only default-OFF selection with both public consumers and the operational witnesses, measuring retrieval/fallback latency and proving exact-pointer CAS. The deployment, credentials and IDs are intentionally absent.

Local-only reader wiring now exists at both public endpoints. It makes zero extra D1 requests by default; the optional flag is absent from runtime configuration. Summary preserves the independent terminal rows, marks a failed shard terminal stale/unknown and keeps unrelated groups. Facility preserves the facility, flights and forecast, but omits an unverified checkpoint and prevents caching that response. A shard row cannot look LIVE without an exact matching source-health event/retrieval and the existing freshness test. Projection preserves raw lower bounds and zero counts, rejects invalid clocks/identity/mixed capture/duplicate zones, and applies the existing 12/24 caps after selecting a single terminal generation. Manifest count proves complete storage of the submitted capture, not complete upstream provider coverage; writer integration must require fully staged source normalization and reject partial generations or record explicit coverage. This does not activate routing or add a production binding.

Release blocker: A4 may return the same observation on several attempts. Existing observation-row dedup preserves the original retrieval, but general source_health can advance its latest retrieval on an unchanged observation. Do not change the row's immutable first retrieval, infer success from matching observed timestamps only, or let a generic later attempt mark an unrelated payload LIVE. Staging writer must atomically relate terminal, exact digest and publication epoch to stable run identity and separate latest verified same-content witness time; current timestamp equality is intentionally fail-closed pending this. Tests must prove: (1) exact same-content later attempt advances only its matching witness, leaves immutable row time and digest fixed, and does not renew observation-age budget; (2) same observedAt but changed zone/value does not validate the old digest; (3) failed, late, or orphaned attempts cannot advance published evidence; (4) matching evidence for the other terminal never validates this terminal.
