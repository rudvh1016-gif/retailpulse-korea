# 관세 뉴스 수집 안전 준비

작업은 main `63e63060058b035fef2312c91b3011a6d463d972`에서 시작했고, 사용자가 UI PR335를 병합한 main `71d6b640bd591a36ce69922d848c18511eafb42a` 위에 충돌 없이 반영했다. 별도 branch/worktree의 코드 준비이며, 실제 수집·운영 DB 쓰기·새 credential/권한·일정·병합·배포는 포함하지 않는다. 완료한 UI 검사를 로컬에서 반복하지 않는다.

## 변경 이유와 최소 저장 범위

기존 수집기는 새로 준비한 빈 요약·날짜·pending 첨부로 승인본을 교체하고, HTML 권리 마크 누락을 다른 근거의 철회로 처리할 수 있었다. `review`/`withdrawn` 상태만으로는 공개가 차단되지 않았다. 이력 400건에 도달하거나 뒤쪽 HTTP 요청이 실패하면 앞에서 확인한 철회까지 저장되지 않았다.

SQL0026과 승인 입력 `data/approved-news/customs-2026-10-10.json`의 bytes/SHA는 바꾸지 않는다. 새 테이블·열·index·migration이 없다. 기존 current JSON에 선택형 `collectionReview`만 추가한다. 기사당 최신 후보 1개, 고정 버전·fingerprint·관측 시각·최대 4개 보류 사유를 보관한다. 후보는 제목·링크·날짜·권리 관측·최대 6개 문서의 링크/이름/검토 SHA만 담으며 승인 요약이나 raw HTML/PDF/이미지를 복제하지 않는다. 전체 payload의 기존 8KiB 제한을 유지한다.

기존 승인본의 공개 필드·수동 요약·권리·시행일·문서 검토·contentFingerprint·semantic_hash·received_at은 수집으로 바꾸지 않는다. 후보만 바뀌는 관측은 승인본의 revision을 만들지 않는다. 관측 시각만 바뀐 반복은 실제 SQLite current/revision 변경 0이다. 새 기사는 항상 비공개 `review`로 보관한다. 제목만으로 기존 승인 분류나 매장 관련성을 낮추지 않는다.

공개 API는 현재 공개 flag와 권리·상태를 모두 검사하고 명시적인 공개 필드 목록만 반환한다. 후보·hold 내부 자료는 nested 값까지 공개 projection에서 제외한다. `review`, `withdrawn`, hold는 공개 불가다. 문서 검토에 필요한 권리 검사와 공개 승인은 별도 함수다. 문서 pending이 하나 남았다는 사실만으로 이미 승인된 다른 근거의 요약까지 취소하지 않는다.

## 근거 변경과 철회

승인된 10174903은 검토 PDF, 10168489는 정책브리핑 공식 전재가 권리 근거다. HTML 마크 부재만으로 이 근거를 지우지 않는다. HTML 자체가 유일하게 기록된 승인 근거인데 확인되지 않으면 재검토 hold로 구분하며, 이를 확정 철회로 기록하지 않는다.

완전한 첨부 목록에서 기존 검토 문서가 사라지거나, 직접 관측한 문서 이름이 바뀌거나, 정확한 기사·공식 첨부 URL에 결합된 bytes의 SHA가 다르면 해당 승인 기사 공개를 보류한다. 바이트 관측은 pending이며 사실·권리를 승인하지 않는다. 각 관측 성공 직후 저장하므로 후속 HTML 권리 검사 실패나 같은 URL의 다른 SHA 관측이 이미 확인한 변경 증거를 취소하지 않는다. 이전 문서·요약·날짜·권리 근거는 그대로 보관한다. 현재 legacy 사실에는 문서별 의존성 매핑이 없으므로 자동으로 일부 문장만 재승인하지 않는다. 같은 링크는 bytes 동일성 증거가 아니다. 문서를 추가 다운로드하지 않으며, 새 사실/시행일의 공개 승격도 자동화하지 않는다.

첨부 목록은 실제 공식 HTML의 닫힌 첨부 행·목록과 모든 항목을 확인했을 때만 완전하다고 표시한다. 속성 순서·따옴표 종류는 무관하다. 누락·잘림·알 수 없는 링크·6개 초과·동일 URL 이름 충돌은 불완전으로 남기며, 이 경우 목록에 없다는 이유만으로 기존 문서가 삭제됐다고 단정하지 않는다.

명시적 철회 검토 입력은 정확한 기사 ID·기사 URL·현재 수신 HTML의 UTF-8 SHA256·원문 철회/공개 중단 문구·검토 시각에 결합한다. 단순한 HTML 마크 부재, 다른 기사/URL/hash/문구는 철회로 인정하지 않는다. 이 SHA는 철회 검토의 바인딩에만 쓰고 일반 후보 fingerprint에는 쓰지 않는다.

검증된 철회는 해당 기사의 기존 `may_publish`를 0으로 먼저 설정한 뒤 후보를 저장한다. 이 작은 indexed UPDATE는 payload를 키우거나 revision을 만들지 않는다. 따라서 revision 400건, 정확히 8KiB인 승인 payload, 뒤쪽 HTTP/파싱 오류에서도 이미 저장한 차단이 롤백되지 않는다. 후보를 추가 저장할 공간이 없으면 오류를 보고하면서 승인 근거와 비공개 flag를 유지한다. DB 자체가 쓰기를 거부하거나 결과가 불명확하면 성공이라고 보고하지 않는다.

수집기는 차단을 자동으로 해제하지 않는다. 승인 hash뿐 아니라 읽은 payload 전체와 공개 flag를 CAS 조건으로 비교해 다른 검토자/수집기의 새 기록을 되돌리지 않는다. 의미 있는 승인본 변경을 저장할 때 revision에는 공개본만 넣는다. 재공개·후보 승격은 별도 명시적 검토 절차가 필요하며 이 작업에서 운영 도구나 자동 승격 경로를 추가하지 않는다.

## 요청·저장 예산

- RSS 4회 + 공식 목록 4회 + 기사 최대 20회 = 제공자 최대 28회. 추가 문서 요청 0, 제공자 재시도 0, 응답 1MiB/15초/redirect 거부를 유지한다.
- 4개 게시판에 모두 후보가 있으면 기사 5개씩 읽는다. 빈 큐의 몫을 다른 게시판에 재분배하고 같은 기사 ID는 전체 큐에서 1회만 읽는다.
- 기사마다 관측을 저장해 뒤쪽 실패가 앞의 검증된 차단을 취소하지 않게 한다. 오류는 정상 완료로 바꾸지 않는다.
- current 200, revision 400, payload 8KiB의 기존 상한과 최대 payload 합계 4.69MiB를 유지한다. 이는 물리 DB 크기·여유 용량·계정 전체 비용의 실측값이 아니다.
- 정상 기존 기사 관측은 indexed current SELECT 1회, 변경된 후보는 UPDATE 1회다. 보류/철회는 별도 bounded UPDATE를 추가한다. 로컬 문서 bytes를 제공하면 각 유효한 관측마다 별도 저장 검사를 실행해 증거가 덮이지 않게 한다. D1 HTTP/SQL 요청은 제공자 28회에 포함하지 않는다. 실제 rows_read/rows_written 및 index amplification은 운영 검증 전 미확인이다.

새 scheduler나 실행 주기를 추가하지 않는다. `CUSTOMS_NEWS_COLLECTION_REVIEWED=false`와 기존 CLI의 compile/runtime gate를 유지한다. 비활성 CLI는 credential 해석·제공자·DB 접근 전에 종료한다. 유료 AI나 새 패키지는 없다.

## 별도 후속

아이콘 검사 후속은 [Issue 336](https://github.com/rudvh1016-gif/retailpulse-korea/issues/336)에 기록했다. 공항 월간 API의 로딩→완료 portal 재마운트와 hook별 캐시로 인한 중복 가능성은 [Issue 337](https://github.com/rudvh1016-gif/retailpulse-korea/issues/337)에 코드 근거와 최소 후속 범위만 기록했다. 이 PR에서는 두 후속의 코드를 변경하지 않는다.

운영 아이콘 smoke는 버전 파일명 `apple-touch-icon-20261007.png` 선언에도 옛 `/apple-touch-icon.png` 문자열을 요구한다. 이 준비 PR이나 UI PR335에 섞지 않고 작은 별도 후속으로 남긴다. 실제 선언 자산과 기존 URL은 읽기 조사에서 모두 200/image/png/19,858B였으며 사이트 장애나 iOS 설치 실패로 단정하지 않는다.

운영 활성화 전에는 공식 이용 조건/주기·계정 전체 사용량·단일 writer/일정·D1 오류/재시도 정책·변경 없는 원격 저장 실측·명시적 후보 승인/재공개 절차를 별도로 검증해야 한다. 기존 승인 입력을 반복 import하여 저장 SQL을 건너뛴 결과는 원격 unchanged UPSERT 검증을 대신하지 않는다.
