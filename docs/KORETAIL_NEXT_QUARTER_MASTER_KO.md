## 1. 정체성: 숫자 모음이 아니라 현장 확인 업무를 줄이는 도구

KORETAIL은 서울 관광상권과 인천공항의 공식·공개 신호를, 현장 근무자가 오늘 무엇을 확인하고 내일 무엇을 준비할지 판단하는 데 쓰도록 정리하는 운영 정보 서비스다.

판매 가설은 ‘공공데이터 보유량’이나 ‘AI가 쓴 긴 설명’이 아니다. 여러 공식 사이트를 확인하는 시간, 중요한 변경을 놓치는 일, 팀원에게 같은 정보를 반복 전달하는 일을 줄이는 것이다. 실제로 줄였는지 측정한다.

브랜드 KORETAIL, 현재 도메인, 기존 공항·명동·홍대·성수 및 4개 언어는 유지한다. 공항은 기존 대표 화면으로 유지하되 기능 확대보다 정확성과 안정성을 우선한다. 전국 관광앱, 예약 중개, AI 챗봇, 자동 여행 일정 생성 서비스로 확대하지 않는다.

### 같은 자료, 다른 현장 판단

- 관광안내: 혼잡을 피할 시간, 공식 행사 확인, 날씨에 따른 준비, 방문객에게 보여줄 근거 있는 안내를 돕는다.
- 매장 운영: 평소와 다른 주변 흐름과 확인할 업무를 보여준다. 주변 인구를 매장 고객·외국인 매출로 바꾸지 않는다.
- 혼잡 증가가 매장에는 기회일 수 있어도 가이드에게는 회피 사유다. 두 사용자에게 같은 ‘높음=좋음’ 점수와 같은 행동을 주지 않는다.

한 데이터 처리 기반을 공유한다. 두 유료 제품을 동시에 새로 만들지 않는다. 먼저 실제 사용하는 한 집단과 하나의 반복 업무를 선택한다.

## 3. 첫 판매 실험: 관광안내 종사자의 기존 업무에서 시작

우선 가설은 ‘오늘 근무·투어 전 확인 브리핑’이다. 이미 있는 Tourism Desk를 보여주며 실제 안내 업무 한 건을 관찰한다. 숙련 가이드가 외워서 해결하는 정보나 지도 앱보다 느린 기능은 유료 가치로 세지 않는다.

### 사용자와 구매자를 구분한다

1. 현업 관광통역안내사·가이드·관광안내 직원: 사용성·오해·반복 수요를 검증할 사용자. 개인 구독 의사는 별도 확인한다.
2. 소규모 인바운드 여행사·가이드 팀 운영자: 여러 직원의 확인·공유 업무를 줄이는 상품의 구매자 가설.
3. 관광안내사 관련 사이트·협회·교육기관: 초기에는 허가받은 참여자 모집·소개 경로. 구매자·제휴사로 확인된 것이 아니다. 재사용·유료 갱신이 나온 뒤 공동 상품이나 삽입형 제공을 검토한다.
4. 관광상권 매장 운영자: 기존 자료로 비교 인터뷰하되, 관광안내와 동시에 별도 제품 개발을 시작하지 않는다.

공식 협회 사이트의 교육·회원·업계 안내는 접근 경로를 확인하는 근거일 뿐 지불의사의 근거가 아니다. 회원 명단 수집, 무단 대량 메시지, 제휴 사실 과장, 협회 로고 사용은 하지 않는다.

### 최소 유료 가치의 후보

방문 지역·날짜·시간대 선택 → 오늘 달라진 사실과 확인할 사항 → 공식 확인 링크 → 미확인 정보 표시 → 팀/관광객에게 보여줄 한 장 정리 → 실제 사용 후 짧은 결과 기록.

기존 복사·방문객 보기 기능을 우선 이용한다. 공유·인쇄도 원래 출처, 적용 날짜, 자료 시각, 한계를 유지한다. 외부 발송은 이용자가 요청한 경우만 한다. 비공개 일정이나 고객 식별정보를 링크에 넣지 않는다.

영업 중 여부, 휴무, 이동시간, 행사 실제 개최 여부, 다국어 고유명칭은 근거가 있을 때만 표시한다. 행사 기간에 오늘이 포함된다는 사실은 ‘현재 운영 중’이 아니다. 확인되지 않은 장소·우회 동선·약국 운영 여부를 AI가 채우지 않는다. 검증 전에는 ‘공식 페이지 확인 필요’가 올바른 결과다.

## 4. 데이터 추가는 금지가 아니라 조건부 투자

새 자료마다 ‘누가 어떤 결정을 바꾸는가 / 현재 무엇을 놓치는가 / 확인 가능한 출처와 이용조건 / 수집·검증·유지 비용 / 채점 가능한 결과’를 한 장으로 적는다.

실제 사용자가 반복해서 필요로 하거나, 현재 핵심 업무의 오류·누락을 줄이거나, 사전에 정한 예측 목표의 외부 검증에 기여할 때만 후보가 된다. API가 존재한다는 이유, 지역 개수를 늘리는 이유, 화면을 채우는 이유만으로 추가하지 않는다.

첫 후보는 기존 데이터 누락·날짜·표시 문제다. 새 관광지 운영시간·공식 다국어 명칭 등은 실제 시험 요청과 데이터 이용 검토를 통과한 한 항목부터다. 상업 이용과 자동 접근 허용을 출처별로 확인한다. 권리 불명확 자료는 유료 상품에서 격리한다.

고객 매출 자료 연결은 필수가 아니다. 확인시간·안내 오류·공유 업무 감소만으로 먼저 실험할 수 있다. 자발적 매장 결과가 필요해지면 별도 동의와 보안 검토를 거친 최소 집계값부터 쓰고, 공개 저장소·공개 이슈·AI 프롬프트에 원본을 넣지 않는다. 다중 고객 데이터 격리·보관·삭제 정책 없이 업로드 기능부터 만들지 않는다.

## 5. 토큰 없는 운영: 기존 부품 위에 얇은 관리층을 추가

하네스는 검사·증거·복구 안전장치이고, 오케스트레이션은 그 장치를 올바른 순서로 실행하는 관리 절차다. AI 에이전트 여러 명이 상시 토론하는 구성이 아니다.

정상 운영 경로:

수집 예정 확인 → 실행 → 원자료 검증 → 저장 확인 → 제공 화면 확인 → 결과 관측·채점 → 이상 분류 → 허용된 복구 → 복구 재검증 → 상태 저장.

이 경로의 LLM 호출 목표는 0이다. 최초 구현, 새로운 오류 수정, 사람의 심층 검토에 쓰는 구독 사용량은 별도다. 서버·요청·저장·사람 시간까지 무비용이라는 뜻은 아니다.

### A. 같은 자료를 말하는지 검사

출처별로 값의 의미·단위·지역·시간대·기준일·발표시각·관측시각·수집시각·갱신주기·정상 지연 범위·필수 항목·쿼터·이용조건을 연결한다. 기존 출처표와 코드가 한 규칙 원본을 바라보게 한다.

자료 합계 검사는 같은 모집단·정의·시간·터미널 범위가 확인된 경우에만 한다. 출국장 예고와 환승 보안검색 예고를 무조건 공식 출국객 총계로 합산하지 않는다. 현재 참고 합계가 있다면 명칭·산식·비교 불가 조건을 유지하고 기존 정확성 시험을 다시 본다. 항공편의 국가를 승객 국적으로, 역 하차를 고유 방문객으로 바꾸지 않는다.

### B. 실행되었는지와 결과가 쓸 만한지 따로 검사

예정 회차, 호출 접수, 시작, 완료, 정상 자료 확보, 저장 확인, 사이트 반영을 다른 칸에 기록한다. HTTP 200·종료코드 0·빈 배열·최근 생성시각 하나만으로 정상 판정하지 않는다.

필드 존재와 실제 유효값, 정상 0건과 조회 실패, 자료 공급 지연과 서버 고장, 수동 복구 성공과 원래 예약 작동을 구분한다. 예상 회차와 조회 범위를 모르면 누락률을 만들지 않는다.

### C. 복구를 실행한 다음 실제 효과까지 검사

아래 허용표 외 작업을 일반 코드가 임의로 만들지 않는다. 복구 전후 근거와 수행 번호를 남기며, 같은 원인에 무한 재시도하지 않는다. 복구 요청 접수는 복구 성공이 아니다. 저장·공개 응답·필요한 화면까지 확인한 후에만 해결로 표시한다.

### D. 관리 프로그램 자체도 시험

격리 시험에서 오래된 날짜, 엉뚱한 지역, 정상 0건, HTTP 200 오류 페이지, 일부 페이지 누락, 잘못된 합계, 저장 실패, 중복 실행, 화면에서 숫자 소실, 비용 측정 불가, 감시기 중단을 주입한다. 정상 사례도 반드시 통과해야 한다.

기존 시험 목록 검사·실제 화면 시험을 재사용한다. 중요 검사 일부는 해당 방어를 제거하면 실패하는지 확인한다. 운영에 가짜 자료를 넣지 않는다. 자동 판정의 조건식을 그대로 복사한 시험만으로 독립 검증이라고 부르지 않는다.

수집기 안의 감시만으로 수집기 전체 중단을 발견할 수는 없다. 기존 인프라 안에서 마지막 감시 시각을 별도로 읽는 관측 경로와 수동 확인 경로를 둔다. 두 서비스가 모두 중단된 경우까지 자동 발견한다고 보장하지 않는다. 새 상시 AI나 중복 수집기를 만들지 않는다.

### E. 비용과 알림 부담도 검사

기존 70/85/95 정책을 재사용하되 계정 전체 사용량, 관측 지연, 공식 측정과 내부 추정을 분리한다. 모르는 사용량은 0이 아니다. 선택적 재수집·과거 채움·대형 검사를 먼저 제한한다. 이미 검증된 필수 증거를 지우거나 유료 플랜으로 자동 전환하지 않는다.

새 일반 코드가 만든 장애 번호·변경점만 보고한다. 같은 상태를 매시간 이슈·댓글로 쌓지 않는다. 동일 사고는 같은 번호로 갱신하고 발생·악화·복구·사람 결정 필요 때 알린다. 조용한 상태와 감시기 미실행을 구분한다.

## 6. 일반 코드의 자동복구 허용표

| 상황 | 자동 허용 후보 | 중단·사람 검토 조건 |
|---|---|---|
| 일시적 통신 실패 | 기존 출처별 시간·횟수·전체 요청 예산 안의 재시도 | 인증·권한·구조 변경은 재시도하지 않음 |
| 잘못된 신규 응답 | 새 응답 격리, 마지막 정상값과 원시각 유지, 지연/불가 표시 | 단위·의미·출처를 추측해서 수정하지 않음 |
| 빠진 수집 회차 | 같은 업무의 영구 중복 방지와 현재 유효기간 확인 후 승인된 회차만 복구 | 실제 진행 여부 불명확하면 두 번째 작업 시작 금지 |
| 화면용 파생자료 누락 | 검증된 원본으로 재생성·재조회, 기존 게시 규칙 적용 | 예측의 사전 시점을 복원한 것처럼 쓰지 않음 |
| 결과 관측 누락 | 허용된 기간의 실제 결과를 수집하고 뒤늦은 수집임을 기록 | 과거 예측을 새로 작성해 사전 예측에 포함하지 않음 |
| 비용·쿼터 압박 | 사전 승인된 선택 작업 제한, 명확한 상태 표시 | 결제·자동충전·새 API·새 서비스 금지 |
| 새 코드/인증/정의 결함 | 근거 묶음과 수정 요청 후보 생성 | 스스로 소스·테스트·권한·데이터 구조를 고치지 않음 |

허용표는 구현·격리 시험·운영 시험·소유자 승인 후 항목별 활성화한다. 이 문서 저장만으로 활성화하지 않는다. 운영 DB 복원·삭제·스키마 변경, 인증 우회, 예측식/가중치/임계값의 임의 변경, 무검토 자동 배포는 금지한다.

## 7. 예측과 업무 효과의 성적표는 분리한다

현재 인구 참고 예측 v1은 과거 같은 요일의 관측을 이용한다. 이 기존 모델과 같은 계산을 이름만 바꿔 비교하여 성능 향상을 주장하지 않는다. 공식 인구 구간의 중간값은 비교 대상인 공식 추정 관측일 뿐 실제 매장 방문·매출의 정답이 아니다.

예측 평가는 같은 목표·지역·단위·시점·발표 가용성을 맞춘다. 자료가 나중에 수정돼도 당시 알고 있던 입력을 보존한다. 실제 날씨를 과거 예측 입력으로 쓰거나, 나중에 알게 된 행사를 사전 탐지한 것으로 세지 않는다.

기존 모델(champion)을 고정하고 후보(challenger)는 격리된 비교에서만 돌린다. 사전에 선택한 같은 요일 기준 등과 동일한 평가 표본·시점으로 비교한다. 평균오차, 누락률, 과대/과소 경고, 놓친 급증, 구간별 안정성, 표본 수를 함께 기록한다. 항상 보통이라고 말해 얻은 높은 적중률을 자랑하지 않는다.

최소 30개의 서로 다른 사전 예측 날짜는 기존 문서의 초기 표본 조건일 뿐 우수성·자동 승격의 충분조건이 아니다. 실제 확보 표본·불확실성·재현성·운영 피해를 검토한 경우에만 PROMOTION_CANDIDATE로 제안한다. 기간이 지났다는 이유로 채택하지 않는다.

놓친 변화의 원인은 데이터 누락/지연/규칙/사용자 선택/원인 미확인으로 분리한다. ‘행사 자료 없음’만으로 실패 원인을 행사로 확정하지 않는다. 모델 없는 규칙은 반복 패턴과 알려진 결손을 찾아 개선 후보를 만들 수 있지만 모든 새로운 원인을 자동 발견하지는 못한다.

사업 평가는 별도다: 같은 실제 업무의 확인시간, 확인한 사이트 수, 자발적 재방문, 공유 사용, 잘못 안내한 사례, 돈을 낸 구매자, 갱신·환불·지원 시간을 본다. 사용자 보고와 직접 측정도 구분한다. 예측이 단순 기준보다 낫지 않아도 확인·공유 도구로서 유료 가치는 별도 검증할 수 있다.

## 8. AI가 정말 필요한 때의 GitHub 인계

평소 일반 코드가 사고/개선 후보를 만들고 허용된 복구부터 한다. 새로운 코드 수정, 반복되는 동일 결함, 해석이 필요한 출처 변경, 사전 승인된 제품 개선만 AI_REVIEW_REQUIRED가 된다. 외부 공급자 장애를 기다리는 일이나 이미 해결된 동일 사고는 AI 호출 이유가 아니다.

원하는 흐름:

일반 코드 진단·복구 → 필요할 때 GPT 검토 → GitHub의 승인된 다음 과제 → 일반 코드 실행 예약 → Claude 개발 → GitHub 보고·검사 결과 → GPT 실제 변경 검토 → 종료 또는 별도의 다음 과제.

### 중요한 비용·지원 경계

- 일반 자동점검과 허용 복구: LLM 호출 0을 검증한다.
- GPT가 GitHub를 읽고 판단하거나 Claude가 개발: 기존 구독 사용량을 소비한다. API 추가 청구 없음과 토큰/사용량 0은 다르다.
- 2026-09-12 공식 ChatGPT 예약 설명은 Pro 모델 제외, 예약의 플랜 사용량 적용, 최대 매시간, 일반 예약 webhook 미지원이라고 안내한다. 계정별 앱 읽기·쓰기와 승인도 시험해야 한다.
- 따라서 ‘GitHub 변화가 생기면 일반 ChatGPT Pro가 즉시 무인으로 깨어남’을 현재 지원 사실로 단정하지 않는다. GPT_EVENT_WAKE_UNVERIFIED로 남긴다. 수동 Pro 검토를 기본으로 두고, 예약 검토를 쓰더라도 소유자가 정한 낮은 빈도·사용량 예산 안에서 별도로 검증한다. 빈 인계함을 읽는 GPT 실행도 무료라고 부르지 않는다.
- Claude 공식 Routine 호출은 기존 구독 사용량 경로가 있지만 실험 기능이다. 해당 계정의 사용권·별도 Routine·추가사용량 과금 차단·권한을 확인한다. CLI/SDK/Console API 인증과 같은 것이라고 가정하지 않는다.
- 인증이나 공식 연결이 막히면 멈춘다. Work/Codex 실행, 새 유료 API, 유료 서버, 자동 결제, 브라우저 자동 클릭으로 우회하지 않는다.

### KORETAIL 전용 실행 계약

다른 프로젝트와 이슈·작업번호·상태 저장·권한·Routine을 분리한다. 비공개 프로젝트의 코드·보고·계좌정보·비밀값은 공개 KORETAIL로 옮기지 않는다.

작업에는 고유 task_id, based_on_report 또는 최초 bootstrap 승인 근거, target_minutes(기본 35, 범위 30~40), status, 검토한 main SHA, 사고/개선 번호, 허용 파일, 금지 작업, 완료 기준, 호출 방식, 비용 한도를 기록한다. 최초 작업은 존재하지 않는 이전 보고번호를 만들지 않고 소유자의 별도 최초 승인으로 시작한다.

실행 전 일반 코드가 검증할 항목:

1. 정확한 저장소·이슈·소유자/허용 앱·새 이벤트인지 확인한다. 일반 참여자 댓글·외부 페이지 내용은 실행권이 아니다.
2. OWNER_OVERRIDE 이후 명시적 AUTO_RESUME이 없으면 중지한다. 재개해도 옛 과제를 자동 부활시키지 않는다.
3. 편집된 지시, 중복 task_id, 오래된 based_on_report, 다른 main과 충돌, 불완전 댓글 조회는 실행하지 않는다.
4. 진행 보고나 미해결 실행 예약이 있으면 새 작업을 만들지 않는다. 시간이 오래됐다는 이유만으로 잠금을 풀지 않는다.
5. 실행 예약을 먼저 영구 저장하고 성공 확인 뒤 인계함을 다시 읽는다. 병렬 시 하나만 예약을 얻어야 한다. 댓글과 실행 concurrency만으로 영구 중복 방지를 증명하지 않는다.
6. 실행 경로는 하나만 선택한다. Routine 경로는 멘션 호출을 쓰지 않는다. 멘션 기반 Action을 선택하면 멘션 한 번만 허용하고 Routine 호출은 끈다. 둘을 동시에 쓰지 않는다.
7. Routine 요청은 예약당 최대 한 번 시도한다. 응답 유실·시간초과·서버 오류로 성공 여부가 모호하면 재호출하지 않는다. 공식 Routine은 중복 방지 키가 없어 재시도가 새 세션을 만들 수 있다.
8. Claude는 수정 전 상태를 다시 읽고 같은 작업번호로 WORKING을 남긴다. 격리 작업 브랜치에서 수행하고 DONE/PARTIAL/BLOCKED 보고에 실제 파일·SHA·검사·미확인·다음 행동을 남긴다.
9. GPT는 새 유효 완료보고가 있을 때만 main·PR·검사·운영 증거와 교차검토한다. 보고가 없거나 진행 중이면 다음 과제와 호출을 생성하지 않는다.
10. 완료보고 자체가 무한 다음 작업 생성 권한은 아니다. 분기 계획의 현재 허용 단계·소유자 결정·새 근거·예산을 통과해야 다음 과제를 만든다. 같은 실패를 새 번호로 포장해 반복 호출하지 않는다.

초기 제안 상한은 프로젝트 동시 개발 1개, 하루 새 실행 예약 최대 2개, 주간 개발 묶음 최대 4개다. 이는 구독 제공량이 아니라 소유자 승인 전 제안 예산이다. 실제 토큰이 안 보이면 UNKNOWN으로 기록하고 세션 수·작업시간·실제 청구/사용량 지표를 따로 기록한다. 35분은 작업 크기 목표이지 반드시 채우거나 정확히 끝내라는 명령이 아니다.

비AI 읽기 시험 → 중복/중지/응답유실 격리 시험 → 과금·권한 확인 → 소유자가 승인한 작은 실제 작업 1회 → Claude 시작/보고·GPT 재검토까지 확인한 후에만 활성 상태로 올린다. ‘설정 저장’, ‘호출 접수’, ‘작업 완료’, ‘운영 반영’은 다른 증거다. 이번 문서 저장에서는 모두 활성화하지 않는다.

## 9. 개발을 위한 개발을 막는 우선순위

우선순위는 개인정보·잘못된 안내·자료 신뢰성의 위험 → 현재 사용자 핵심 경로 장애 → 반복 수작업 감소 → 관측 가능한 판매/사용 실험 → 나머지 제안 순이다.

일반 코드가 고정된 규칙과 실제 사고 횟수·사용 경로·재현 근거로 개선 후보를 정리할 수는 있다. 점수가 높다는 이유로 권한을 확대하거나 임의 과제를 시작하지 않는다. 모든 기능은 어떤 사용자 업무·위험·지표를 바꾸는지 설명해야 한다.

AI 비용을 줄이는 방법은 검사를 없애는 것이 아니다. 기존 검사 묶음을 재사용하고, 변경 범위별 검사 뒤 필요한 전체 검사를 한 번 수행하며, 동일 문서·전체 인계 이력을 매번 다시 읽히지 않는 것이다. 사고 묶음에는 관련 파일과 실패 전후 사실만 넣고 긴 원본은 링크로 남긴다.

## 10. 최초 14일: 허용 범위가 좁은 첫 단계

시간 제안: 첫 14일 전체 12시간 이내. 인터뷰·판매 준비도 여기에 포함한다. 막히면 범위를 줄이며 초과 투입을 자동 승인하지 않는다.

- 기존 코드·현재 설정·자연 실행 증거·오래된 문서의 차이를 정리한다. 실제 배포 입력 비교로 문서 전용 배포를 막는 작은 수정안을 첫 안전 과제로 검토한다. 단순 경로 제외로 필수 검사를 끄지 않는다.
- 기존 진단을 묶은 읽기 전용 상태표를 만들고, 핵심 데이터부터 원본→저장→제공까지 확인한다. 대형 자동운영 플랫폼을 새로 만들지 않는다.
- 첫 주부터 기존 Tourism Desk로 현업 가이드/안내 직원 3~5명 참여를 확보한다. 가능하면 소규모 여행사 구매 담당 2~3곳도 인터뷰한다. 사용자와 구매자 수를 구분한다.
- 실제 업무 한 건을 기존 방법과 KORETAIL로 수행한 시간·오해·재방문을 기록한다. 인터뷰가 안 잡힌다고 개발 과제를 늘리지 않는다.
- 기존 예측·결과 기록이 실제로 쌓이는지 확인한다. 상위 모델·새 자료 없이 기록 누락부터 점검한다.
- 14일에 계속 시험할 집단과 한 업무를 고른다. 이는 2~4주 반복 사용 기준을 통과했다는 뜻이 아니다.

## 11. 30·60·90일 조건부 계획

달력 기준은 소유자가 첫 검증을 시작한 날을 Day 1로 기록한다. 문서 작성일만으로 실험이 시작됐다고 하지 않는다. 총 90일 투입 상한 제안은 80시간이며 새 구독·업그레이드·새 유료 API 비용은 0을 기본으로 한다.

| 시점 | 주요 결과 | 다음 단계에 갈 조건 | 조건을 못 채우면 |
|---|---|---|---|

수납이나 재방문 수의 예시는 통계적 시장성 증명이 아니라 자원 배분 기준이다. 대조군 없이 업무 개선을 제품의 인과 효과라고 단정하지 않는다. 미래 예측 표본이 부족하면 기간이 지나도 성능 주장을 보류한다.

## 12. 가격·투자 회수의 현실적인 기준

아래는 인터뷰에서 시험할 가설이지 확인된 시장 가격이나 판매 전망이 아니다.

- 개인 가이드: 월 9,900~19,900원 후보. 단순 정보 모음이라면 무료 대안 때문에 안 살 가능성을 기본적으로 고려한다.
- 소규모 여행사·가이드 팀: 월 39,000~69,000원 후보. 한 담당자의 정리·팀 공유 시간을 실제로 줄일 때만 시험한다.
- 리테일 별도 상품: 반복 사용과 다른 구매자 근거가 있을 때만 범위를 정한다. 매장 자료 연결을 미리 의무화하지 않는다.

월 19,900원 17명은 매출 338,300원, 월 49,000원 7팀은 매출 343,000원이다. 고객을 그만큼 확보할 수 있다는 전망도, 이익도 아니다. 개인 저가 구독의 지원 부담이 커지면 오히려 적자일 수 있다.

수납 - 환불 - 결제/전달/데이터 등 추가 변동비 = 현금 기여액으로 구분한다. 이 금액과 해당 월 실제 AI 구독·서비스 비용을 비교하고, 소유자 시간은 따로 비용화해 본다. 프로젝트에 필요한 증분 구독비와 개인 전체 AI 지출 회수 목표를 구분한다. 과거 지출은 계속 투자해야 할 이유가 아니다. 90일 동안 매출 0원도 현실적인 결과로 둔다.

유료 고객이 없는데 회원관리·결제·팀 권한·고객사별 맞춤 개발부터 하지 않는다. 초기에는 명확한 제공 범위와 취소 조건으로 작은 유료 시험을 제안한다. 영업·결제·외부 발송·약관 변경은 별도 실제 사용자 승인과 필요한 검토를 거친다.

## 13. 경력 자산은 첫 달부터 따로 만든다

포트폴리오 목표는 ‘AI가 복잡한 코드를 많이 만들었다’가 아니다. 현장 문제 정의 → 자료 의미와 한계 → 우선순위 결정 → 검증 가능한 운영 개선 → 사용자 시험 → 비용·성과 판단을 보여주는 것이다.

적합한 활용 가설은 리테일 영업운영·운영기획·데이터 활용·업무개선·디지털 전환 직무다. 특정 회사 합격·연봉 상승 또는 전문 개발자 역량을 보장하지 않는다.

남길 증거: 1쪽 문제 정의, 고객 업무 전후 비교, 데이터 흐름도, 대표 오류 2~3건의 재현과 방지, 실제 측정한 운영 지표, 유료/거절 가설 검증, 3분 시연, 본인 결정과 AI 작성 부분의 구분. 공개 포트폴리오는 허가된 공개 데이터와 익명 집계만 쓴다. 회사 내부 매출·거래처·직원/고객 정보는 제외한다.

기능 수·테스트 수·PR 수를 성과로 대신하지 않는다. 매출이 없으면 없다고, 직접 측정하지 않은 시간 절감은 미확인이라고 쓴다. 지원서·면접 준비를 Day 90까지 미루지 않는다.

## 14. 진행·축소·중단 판단

권고: 3개월 무조건 개발이 아니라, 첫 14일 제한 실험을 승인하고 근거가 있을 때만 30·60·90일을 이어간다.

상업 관점만 보면 현재 반복 사용·수납·갱신이 확인되지 않아 3개월 비용 회수는 확신할 수 없다. 운영 자동화와 사용자 검증을 함께 남기면 경력 활용의 실질적 자료가 될 수 있으므로 제한된 시간의 실험 가치는 있다.

다음은 중단/축소 사유다: 고객을 만날 계획 없이 자동개발만 반복, 실제보다 부풀린 예측/안내, 새 비용·지원 시간 급증, 해결되지 않은 개인정보·권리 문제, 자발적 사용 없이 기능만 증가, 실패를 인정하지 않으려고 기준을 계속 낮춤.

최종 선택은 사업 확장 / 작은 유료 서비스 유지 / 경력용 완성 후 유지보수 / 종료 중 하나로 기록한다. ‘포트폴리오가 되니까 무조건 계속’도 허용하지 않는다.

## 15. 구현 승인과 문서의 관계

이 기준안은 기존 제품 방향과 검증 문서를 이어받는다. 새 요청에 따른 상업 실험과 조건부 90일 계획을 제안하지만, 현재 재방문·개인정보·정확성 기준을 낮추지 않는다. 과거 문서의 초기 설정 상태는 역사 기록이며 현재 상태 증거가 아니다.

Pro 재검토 후 충돌표와 수용/거절 이유를 남기고 기준안을 승인한다. 그 뒤 각 작업을 작은 별도 PR로 수행한다. 문서 전용 배포 차단, 실제 계정 권한·추가 과금 차단·인계 시험이 끝나기 전에는 무인 개발·자동 병합·자동 배포를 켜지 않는다.

이 문서와 별도 Pro 재검토 프롬프트를 저장한 사실만 보고하고, 하네스 완성·Claude 호출·예약 생성·3개월 자동개발 시작으로 보고하지 않는다.
