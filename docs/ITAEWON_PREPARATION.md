## 실제 저장한 것

`lib/prepared-areas/itaewon.ts`에 기존 `AreaMapping`의 자료형을 재사용하는 준비 데이터를 저장했다. 실제 지역표(`lib/areas.ts`)는 이 파일을 가져오지 않는다. 새로운 활성화 플래그·API·서버·유료 의존성은 없다.

현재 `allAreaIds = Object.keys(areaMappings)`이며 여러 수집기가 이를 순회한다. 따라서 곧바로 지역표에 넣으면 수집량을 늘리는 부작용이 있다. 이번 PR은 이 연결을 하지 않는다. 메뉴·개인 설정·공개 route·sitemap·예측 허용 지역은 기존 세 지역 그대로다.

## 9월 27일 이후 필요한 별도 활성화 검토

- 오너가 실제 공개 범위를 승인한 뒤 기존 서울 도시데이터·생활인구·추정매출·날씨 공급 구조에 하나씩 연결한다. 새 키 발급 없이 기존 키를 쓴다.
- 실시간 정상 수집은 세 POI에서 네 POI가 되어 1회당 1호출 증가(33.3% 증가)한다. 현재 재시도 정책을 포함한 실제 호출·D1 읽기/쓰기와 쿼터를 측정한다. 이번 PR은 증가시키지 않는다.
- 예보 격자는 기존 서울 세 격자와 달라 하나가 추가된다. 실제 격자·수집 시각·누락 처리를 확인한다.
- 이태원 자료의 실제 응답·시각·부분 실패·변경 없는 재수집·누락 시 표시를 검증한다. 이번에는 인증된 수집이나 D1 쓰기를 실행하지 않았다.
- 행사 중심 좌표/반경과 지하철 대상역은 확보 값이 없으므로 만들지 않았다. 공식 경계 검토 후 확정하거나, 해당 자료를 미제공으로 명시해야 한다.
- 네 언어 표시·공개 주소·canonical/hreflang/sitemap·개인 설정은 데이터 준비 확인 후 함께 검토한다. 준비 PR을 병합하는 것만으로 이태원이 나타나지 않는다.

이 PR은 준비 데이터 보존 완료이며, 실서비스 수집·공개 활성화 완료라는 뜻이 아니다.

## 단계 A — 실시간 도시데이터만 수집 (2026-09-28 KST)

오너 지시("모두 차례대로 진행")에 따라 이태원을 **한 공급원씩** 연결한다. 이번 단계는 서울 실시간 도시데이터(OA-21285, POI004) 하나다. 화면·주소·sitemap·예측·다른 수집기는 그대로 세 지역이다.

### 연결 전 실제 응답 확인

- 읽기 전용 계약 점검 `scripts/probe-seoul-citydata-contract.ts`에 POI004를 추가하고 GitHub Actions `import-oneshot.yml`(PROBE)로 실행: 실행 `36357423937`, 브랜치 `work/itaewon-contract-probe` 커밋 `44b7e11`.
- POI004 결과: `httpOk=true`, `officialCode=INFO-000`, 인구·상권 블록 존재, 필수 상권 필드·업종 배열·결제 건수/금액 범위·지역 식별 필드 모두 있음, 시각 형식 `compact-kst-minute` — 기존 POI003/POI007/POI068과 같은 형태. 값은 로그에 남기지 않는 점검이다.

### 코드 계약

- `lib/areas.ts`: `publicAreaIds`(세 지역)와 `realtimeAreaIds`(세 지역+이태원)를 분리. `allAreaIds`는 등록된 네 지역 전부.
- 실시간 수집(`collectSeoulRealtime`)만 `realtimeAreaIds`를 돈다. 수집 상태 문구는 `areas ok n/4`가 된다.
- 행사 중심 좌표·반경은 확인 값이 없어 `null`. 행사 연결은 `publicAreaIds`만 돌고, 중심이 없으면 건너뛴다.
- 지하철 대상역은 확인된 OA-22723 역 코드가 없어 `itaewon: []`. 요청 대상은 세 지역 그대로.
- 날씨 격자(60,126), 생활인구(외국인), 추정매출, 점포 증감, 목적별 이동, 예측 생성은 세 지역 그대로. 각각 실제 응답 확인 후 별도 단계에서 연결한다.
- 수집 범위 점검(`area_data_coverage`)은 실시간과 같은 네 지역을 계산한다. 예측 준비 상태(28일 이력)를 공개 전부터 확인하기 위함이다.
- 운영 증거(`lib/operational-evidence.ts`)는 공개 화면과 대조하는 장치이므로 공개 세 지역만 본다.

### 무료 한도 영향 (INTERNAL_ESTIMATE, 공식 사용량 아님)

- 실시간 주기 15분(하루 96회) × 1호출 = 서울 OpenAPI 호출 하루 +96회(288→384, +33.3%). 서울 인증키의 공식 일일 한도 수치는 이 저장소에 기록된 근거가 없어 적지 않는다.
- D1 쓰기 상한 추정: 회당 현재값 1 + 상권 1 + 맥락 1 + 12시간 예보 최대 12행 = 15행 → 하루 최대 약 1,440행. D1 Free 하루 100,000행 쓰기 대비 약 1.4%. 변경 없는 재수집은 기존과 같이 쓰지 않는다(`source_hash` 비교, 예보는 `DO NOTHING`).
- 공개 요약 API는 이태원을 읽지 않으므로 읽기 증가는 없다.
- 저장량: `seoul_realtime_area`·`seoul_realtime_forecast`·`seoul_realtime_commercial`에는 현재 삭제 보존 정책이 없다(기존 상태, 이번 변경 아님). 따라서 이 세 표의 증가 속도가 약 1/3 늘어난다. 보존 등급 적용은 별도 과제로 남긴다.

### 공개 범위

- 네 언어 페이지 `/{locale}/itaewon`과 관광안내 `/{locale}/tourism-desk/itaewon`을 추가했다. sitemap은 52개에서 60개 URL이 된다.
- 요약 API, 행사·예측 API, 지역 탭, 개인 브리핑 장소, 404 링크, 오늘의 답·공유 미리보기에 이태원을 넣었다.
- 모든 수집기가 네 지역을 수집한다: 실시간, 날씨, 외국인 생활인구, 목적별 이동, 추정매출, 점포 증감, 지하철, 행사, 예측 생성.

- 매핑 버전 문자열은 바꾸지 않았다. 기존 세 지역의 매핑은 변하지 않았고, 버전을 바꾸면 쌓여 있는 이력이 공개 화면에서 사라지기 때문이다.
