## Cause and truth boundary

The shift picker offers 30-minute steps, but the selector rejected every non-hour boundary before inspecting history. Thus a 06:30–15:30 shift always showed an unavailable comparison even with valid current flights and complete hourly history. The closed details contained the reason; the main comparison and share text did not.

Raw scheduled times are retained in `airport_flights`; the existing profile only exposed 24 hourly bins. October 28 and October production availability has **not** been verified: the public reads returned HTTP 403. This work does not claim those raw records exist or that all 31 dates can be upgraded.

## Smallest stored-data extension

- Keep profile version 1 and its existing hourly, total, side and destination fields. Add optional `halfHours` with 48 exact scheduled-KST bins. Use the same newest physical records and cancellation rule. Invalid clocks do not gain precision.
- A precise profile must have 48 nonnegative integer bins, each adjacent pair equal to its existing hourly bin, and matching totals. T1 combines main-building and concourse bins only when both are valid. Side-specific historical comparisons remain unsupported.
- Old profiles still support whole-hour comparisons. Half-hour shifts include only verified dates; missing/invalid dates never enter a monthly denominator as zero. Arbitrary finer minutes and overnight shifts remain explicitly unsupported. Start is included and end excluded.
- The public projection keeps absent legacy precision undefined and rejected precision null, so invalid history is not relabelled as a merely missing upgrade.
- Expose the actual reason on the main comparison and shared copy, not only inside details. Do not round shift boundaries or split an hourly count proportionally.

## Preparation, cost and concurrency

The existing Actions daily profile builder emits the extension on future successful runs. Its normal 0–28-day rebuild window alone cannot cover the beginning of the previous month. The existing `prepareAirportMonths` raw read already covers previous-month start through yesterday, indexed by direction and scheduled time, with a 40,001-row sentinel. Reuse those same rows to enrich existing older daily rows; do not add providers, tables, schedules or visitor-time raw reads.

Older profiles receive only the optional field, and only when their complete, current-classification profile matches the full raw reconstruction after removing `halfHours`. Existing source-hash integrity is checked. If source corrections make the old profile disagree, precision is withheld rather than mixing a new profile with an old summary. Preserve all other payload fields. No missing daily row is created. With no raw rows, only an already-complete all-zero profile matching the empty reconstruction can qualify; missing/incomplete days cannot become zero days.

Each semantic change uses source-hash compare-and-swap. A changed anchor's in-memory hash is advanced before the final monthly CAS. Conflicts stop the attempt and return the count of already-completed writes. Failed writes report that confirmed count. A rejected write response additionally reports `OUTCOME_UNKNOWN`: the attempted statement may have committed, so a retry must reread stored state. Raw adapter errors and causes are not retained because they may contain response secrets. Partial progress is safe to retry; the marker is published only after the eligible attempt finishes. `shiftProfileVersion` marks an attempted upgrade, **not** full monthly coverage. A same-day old rollup without the marker triggers one bounded read; the next unchanged marked attempt has no raw read or write. The cap is checked before any upgrade write.

Visitor database reads remain one indexed range of at most 63 existing daily rows. The maximum additional returned T1/T2 precision is 63 × 2 × 48 = 6,048 small integers, not 31 extra HTTP requests. Stored precision adds 3 × 48 counters per upgraded day. Initial upgrade writes are bounded by the retained existing-row set; subsequent semantic no-op writes remain zero. Actual D1 read/write metrics and Worker CPU are not inferred from local SQLite tests and still require authorized production observation.
