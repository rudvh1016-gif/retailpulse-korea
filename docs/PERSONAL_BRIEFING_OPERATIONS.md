## 사용자 화면

다음 방문: 이 기기에 저장된 설정으로 개인 브리핑을 먼저 보여줍니다. 지역·날짜 전환 → 요약 → 선택한 지표 → 근거가 있는 확인 권장사항 → 자세히 보기 → 작은 피드백 순서입니다. 기존 상세 자료는 아래 펼쳐보기 또는 원래 주소로 접근할 수 있습니다. 설정에서 확인·변경·처음부터 다시 설정을 제공합니다.

자료의 한계: 공항 예상 출국객은 날짜와 전체 시간대가 확인된 공식 예상만 표시합니다. 탑승동은 T1 예상 이용객을 가져다 쓰지 않습니다. 자료가 없는 항공편은 0편으로 표시하지 않습니다. 항공사의 등록 국가는 승객 국적이 아닙니다. 서울의 일부 시간대 혼잡 예측을 내일 하루 전체 예측으로 부르지 않습니다. 과거 외국인 생활인구는 과거 자료라고 표시합니다. 날씨·행사는 선택 날짜로 걸러냅니다. 현재 요약에 공항 날씨가 없으므로 공항 설정의 날씨 선택지는 만들지 않았습니다. 추천 인력 숫자·재고 증가율은 만들지 않습니다.

## GA4 연결 순서 — 운영 반영 전에 설정

2026-09-08 설정 완료: KORETAIL 속성의 KORETAIL Web 스트림과 사용자가 발급한 실제 측정 ID가 일치함을 확인했습니다. 해당 스트림의 향상된 측정을 끄고 저장된 비활성 상태를 확인했습니다. GitHub production 환경에 실제 측정 ID와 NEXT_PUBLIC_GA4_ENABLED=true를 등록했습니다. 실제 ID는 소스에 하드코딩하지 않습니다. 이 설정은 다음 승인된 배포 빌드에 적용되며, 이번 작업에서는 운영 배포를 실행하지 않습니다.

1. GA4에서 https://koretaildata.com 웹 데이터 스트림을 만듭니다.
2. 해당 스트림의 **향상된 측정(Enhanced Measurement)을 모두 끕니다.** 페이지 조회·스크롤·사이트 검색·양식 등 자동 수집을 끕니다. Google Signals와 광고 개인 최적화도 활성화하지 않습니다. 자동 사이트 검색은 URL 검색어를 수집할 수 있고, send_page_view:false만으로 자동 기록을 모두 막을 수 없습니다.
3. GitHub 저장소 Settings → Environments → production → Variables에 실제 NEXT_PUBLIC_GA4_MEASUREMENT_ID를 넣습니다.
4. 2번이 완료되었음을 확인한 다음에만 NEXT_PUBLIC_GA4_ENABLED를 true로 넣습니다. ID만 넣거나 이 값이 없으면 수집은 켜지지 않습니다. 두 값 모두 공개 설정이며 서비스 키가 아닙니다.
5. PR을 반영하고 기존 배포 절차를 별도로 진행한 뒤, 이용 통계 선택에 동의한 브라우저로 GA4 실시간 화면을 확인합니다. 이 작업에서는 운영 배포와 실계정 수신 확인을 하지 않습니다.
6. 필요한 경우 맞춤 측정기준을 이벤트 범위로 등록합니다: role, location, terminal, day, interests, language.

지원 이벤트: onboarding_started, role_selected, location_selected, interests_selected, briefing_preference_selected, onboarding_completed, briefing_viewed, briefing_helpful_yes/no, briefing_used_for_work_yes/no, pwa_install_prompt_seen, pwa_installed.
설정 시작 이벤트는 이용 통계 동의 후 기록합니다. 동의하지 않은 사람·분석 차단 브라우저는 집계에 포함되지 않으므로 전체 방문자 수와 같지 않습니다. 설치 안내 열기는 실제 설치 완료와 구분합니다. iPhone의 수동 홈 화면 추가는 appinstalled 이벤트가 없어 설치 완료를 모두 집계할 수 없습니다.

이름·이메일·회사명·자유입력·검색어·전체 방문 URL·방문 전 페이지를 맞춤 이벤트에 싣지 않습니다. 공개 선택값만 허용하고 광고 기능을 끕니다. GA4 자체의 기기 식별/쿠키까지 완전 익명이라고 부르지는 않습니다. 동의 철회는 이후 전송을 중단하며 이미 전송된 기록을 삭제하지는 않습니다.

피드백은 이 기기에서 날짜·역할·지역·터미널·질문별 한 번씩 기억합니다. 새로고침과 일반적인 재방문 반복 클릭을 막고 최근 100개만 보관합니다. 자료를 지우거나 다른 기기로 보내는 중복까지 완전히 막는 사용자 식별 시스템은 만들지 않았습니다. GA4가 없거나 동의하지 않으면 의견은 기기에만 남고 중앙 집계는 없습니다.

## PWA / Web Push 알림

현재는 설치용 이름·아이콘·시작 주소·전체 화면 설정과 Android/iPhone 설치 안내가 있습니다. 설치하지 않아도 설정은 저장됩니다. 서비스 워커, 푸시 구독 보관, 발송 기능은 없습니다. 따라서 지금 상태 그대로 매일 알림을 보낼 수는 없습니다. 브리핑은 인터넷에 연결되어야 최신 자료를 볼 수 있습니다.

추가 개발 시 필요한 것: 명시적인 알림 신청/해제, 기기별 구독 주소와 암호화 키를 안전하게 저장하는 최소 기능, 서비스 워커, VAPID 서명 키, 만료된 구독 삭제, 정해진 시각에 제한된 건수만 보내는 발송 작업. 브라우저별 수신 테스트가 필요합니다.

iPhone/iPad는 iOS/iPadOS 16.4 이상에서 홈 화면에 추가한 웹앱과 사용자 조작을 통한 알림 허용이 필요합니다. Android의 지원 브라우저에서는 일반 웹사이트에서도 권한 허용 후 푸시가 가능하지만 브라우저·절전 설정 등에 따라 지연될 수 있습니다. Apple 유료 개발자 가입은 웹 푸시에 필수가 아닙니다.

가장 단순한 후보: 기존 공개 GitHub 저장소의 표준 실행 환경에서 하루 한 번 제한된 발송 작업을 수행하고, Cloudflare는 구독 등록/해제와 기존 자료 읽기만 담당합니다. 현재 다섯 개의 수집용 Cron을 늘리거나 바꾸지 않습니다. 실제 구독 보관에는 별도 승인된 저장 구조가 필요하므로 이번 PR에 D1 변경은 없습니다.

예상 비용: 작은 규모에서는 별도 유료 SaaS 없이 추가 고정비 0원을 목표로 설계할 수 있지만 현재 사용량, 구독자 수, 발송 암호화 시간과 재시도량을 측정하기 전에는 무료 운영을 보장할 수 없습니다. 한도에 가까워지면 발송을 줄이거나 멈추며 유료로 자동 전환하지 않는 방식이 안전합니다. 이 설명은 설계 후보이며 구현·활성화가 아닙니다. 실제 구현은 별도 승인이 필요합니다.

공식 근거: [WebKit iOS 웹 푸시](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [Apple 웹 푸시](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers), [Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API), [Cloudflare Workers 한도](https://developers.cloudflare.com/workers/platform/limits/), [D1 한도](https://developers.cloudflare.com/d1/platform/limits/).

## 이번 변경의 운영 부담

새 자료 공급자/데이터 쓰기/수집 스케줄/가입/결제/LLM은 없습니다. 개인 브리핑 계산은 사용자 기기에서 기존 요약 응답을 재사용합니다. 오늘 기본값은 기존 요약 요청을 공유하고, 내일 기본값은 기존 날짜별 요약을 한 번 추가로 읽습니다. 새 화면은 별도 화면 코드 묶음으로 분리했습니다. GA4는 활성화 설정과 사용자 동의가 모두 있어야 비동기로 불러옵니다. 기존 전체 데이터 화면은 서버에서 계속 출력됩니다. 실제 운영 트래픽의 응답 속도·Cloudflare CPU·무료 한도 여유는 운영 배포 없이 검증했다고 주장하지 않습니다.

### 실제 ID 적용 검증 기록 (2026-09-08)

- GA4 관리 화면에서 KORETAIL Web / https://koretaildata.com의 측정 ID 일치를 확인하고 향상된 측정을 비활성화했습니다. Google Signals와 사용자 제공 데이터 수집은 활성화되지 않은 상태임을 확인했습니다. 앱 태그는 광고 저장·광고 사용자 데이터·광고 개인 최적화를 거부하고 Google Signals를 끕니다.
- 실제 production 환경 ID를 적용한 로컬 브라우저 테스트에서 Google 스크립트 요청을 가로채 실제 계정으로 테스트 이벤트를 보내지 않았습니다. 동의 전 태그 0개, 동의 후 정확한 ID의 태그 1개, 온보딩 6개 이벤트·브리핑 조회·도움 피드백 이벤트를 확인했습니다.
- 이메일과 이름이 들어간 시험용 URL에서도 전송 큐에 해당 값이 없으며, 방문 주소는 origin만 포함했습니다. 동의 철회 후 ga-disable 활성화를 확인했습니다.
- ID만 있고 활성화 값이 없거나 false인 경우에는 동의해도 태그를 만들지 않는 회귀 테스트를 추가했습니다. 운영 수신 확인은 PR 반영과 별도 운영 배포 후에 가능합니다.
