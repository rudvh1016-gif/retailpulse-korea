작성일: 2026-09-12 KST
용도: 아래 내용을 새 ChatGPT Pro 대화에 붙여넣는다. 이 파일은 실행 중인 작업 지시가 아니다. 자동 호출, 예약 생성, 운영 코드 변경 또는 병합을 승인하지 않는다.

## 2. 목표와 현실 제약

목표 1은 유료로 반복 사용하는 고객을 통해 운영·AI 비용을 회수하는 것이다. 목표 2는 수익이 부족해도 현장 업무개선·데이터 활용·운영기획에 연결되는 검증 가능한 경력 자산을 남기는 것이다. 다만 포트폴리오라는 이유로 무제한 개발을 합리화하지 않는다.

90일 동안 무조건 기능을 만드는 것이 아니라 최초 14일, 30일, 60일, 90일에 유지·축소·전환·종료를 판정한다. 구독료는 이미 부담되는 비용이다. 현재 구매할 수 없는 상위 GPT 요금제나 더 비싼 Claude 플랜을 해결책으로 전제하지 않는다. 기존 구독 활용, 새 유료 실행비 0, 시간 상한 안에서 계획하라.

KORETAIL은 공식·공개자료를 현장 업무의 확인·준비·공유로 연결하는 도구다. 일반 관광객용 종합 여행앱, 예약·지도·챗봇으로 확대하지 않는다. 공항 대표 화면은 유지하고, 관광안내사·가이드·소규모 인바운드 여행사 대상의 반복 업무를 먼저 시험한다. 안내사 관련 사이트·협회는 잠재 소개/배포 경로이지 확정 구매자가 아니다.

## 4. 이전 답변의 과장을 먼저 걷어내라

관광안내 화면과 인구 참고 예측은 이미 존재한다. 새로 만드는 방향으로 계획하지 않는다. 기존 예측은 과거 같은 요일 기반이며 자기 자신을 기준선으로 놓고 성능이 좋아졌다고 할 수 없다.

‘3개월이면 돈을 번다’, ‘기관 두 곳만 팔면 된다’, 임의 성공확률·AI 실력 점수, 가상의 적중률·매출증가를 사실처럼 쓰지 않는다. 기존 예시 숫자는 실제 실적이 아니다. 고객이 확인·공유 시간을 아끼는 가치는 예측 우수성과 별도로 검증한다.

데이터 추가는 일괄 금지가 아니다. 실제 업무의 누락·오류를 줄이거나 사전에 정한 성능/범위 검증에 필요한 자료만 추가 후보가 된다. 이용권·수집비·유지비·한계도 함께 본다.

## 5. 토큰 없는 자율 운영의 정확한 범위

일반 코드만으로 수집 예정/실행/자료 검증/저장/사이트 표시/결과 채점/오류 분류/허용 복구/복구 재확인을 수행한다. 정상 운영 LLM 호출 0은 실행 경로와 시험으로 증명해야 한다. ‘AI가 정상인지 물어보는 예약’을 0토큰 감시라고 부르지 않는다.

감시자가 자신의 누락을 감출 수 없도록 독립 관측, 마지막 감시 시각, 장애 주입·정상 대조·중요 방어 제거 시험을 설계한다. 수집기와 감시기가 같이 죽는 경우도 한계로 밝힌다.

원자료 형식 변경, 정상 0건/오류 페이지 구분, 시간대, 부분 누락, 합계의 모집단, 격리 자료의 화면 노출, 최신 시각으로 덮은 옛 자료, 발행 실패, 비용 관측 불가, 중복 작업을 반드시 검토한다.

자동복구는 사전 승인된 재시도·격리·마지막 정상자료 유지·안전한 파생자료 재생성·선택 작업 제한까지만 한다. 과거 예측·원본·운영 데이터 소급 변경, 인증 변경, 출처 대체, 새 비용, 전략/예측식 자동 변경, 검사 무력화는 금지한다. 스스로 모든 새로운 버그를 이해하고 코드를 고친다고 과장하지 않는다.

현재 부품을 새로 만들지 말고 필요한 연결을 보강한다. 문서 전용 변경의 불필요한 배포를 막되 실제 배포 입력·필수 검사·배포 증거는 보존한다. 새로운 예약을 만들기 전에 기존 Cloudflare/GitHub 역할과 한도를 대조한다.

## 6. 정말 필요한 때만 GPT↔GitHub↔Claude

일반 코드의 진단/복구로 해결되지 않는 사고나 승인된 제품 과제에만 AI를 쓴다. 목표는 GPT가 실제 근거를 검토해 과제를 GitHub에 남기고, Claude가 읽어 작업하고 결과를 GitHub에 남기며, GPT가 실제 변경과 결과를 다시 검토하는 구조다.

아래를 공식 최신 문서와 실제 계정에서 확인하라. 공식 기능·계정 제공·설정·첫 실제 성공을 구분한다:
- 일반 ChatGPT 예약과 Pro 모델·연결 앱·webhook 지원은 같은 사실이 아니다. 일반 코드가 ChatGPT Pro를 이벤트로 깨울 수 없으면 GPT_EVENT_WAKE_UNVERIFIED로 남기고, 수동 검토 또는 명시적으로 사용량을 배정한 저빈도 예약을 대안으로 구분한다.
- Claude Routine 구독 사용 경로와 Console 유료 API/CLI/SDK 인증을 혼동하지 않는다. 추가 사용량 과금이 막혔는지 확인 전 자동 호출은 끈다.
- Routine은 중복 방지 키가 없을 수 있다. 불확실한 전송 결과를 다시 호출해 세션을 늘리지 않는다.
- Routine 호출과 멘션 Action을 동시에 쓰지 않는다. Routine은 멘션 없이, 멘션 경로는 해당 호출 한 번만, 반대 경로는 비활성으로 설계한다.

KORETAIL 전용 인계함과 영구 상태를 사용한다. 다른 비공개 프로젝트는 참고하더라도 그 코드/지시/비밀값/개인정보를 공개 저장소에 복사하지 않는다.

검사해야 할 안전 조건: OWNER_OVERRIDE/AUTO_RESUME, 고유 task_id, based_on_report, target_minutes 30~40(기본35), main SHA, 허용 범위, 실패 식별값, 신뢰된 작성자, 새 이벤트, 편집/누락/중복 거부, 영구 실행 예약과 재조회, 한 작업만 진행, WORKING/완료보고/CI 교차검토, 중복 호출 금지, 같은 실패 반복 금지, 시작 여부 불명확하면 중지, 명시적 최초 작업 승인, 정상 상태 무알림.

보고서가 올라왔다는 이유로 다음 개발을 무한 생성하지 않는다. 새 근거와 현재 단계·예산·허용 과제가 있어야 한다. 실제 사용량이 안 보이면 숫자를 만들지 않는다.

## 7. 상품과 고객을 냉정하게 검토하라

가이드 개인, 여행사·팀 구매자, 협회·관련 사이트 배포 채널을 구분한다. 각각 이미 쓰는 무료 도구와 업무를 확인하고 무엇을 대체하는지 검토한다. 인터뷰 가능한 현업과 돈을 낼 사람이 일치하는지도 확인한다.

현재 화면으로 첫 주부터 시험 가능한 상품 한 개를 선택한다. ‘오늘 달라진 사항과 공식 확인 링크를 팀/관광객에게 전달하는 브리핑’이 유력 가설이지만 더 나은 좁은 업무가 있으면 반박하라.

행사 기간과 실제 운영, 등록 운영시간과 현재 영업, 혼잡과 구매, 항공편 국가와 국적, 공식 추정 관측과 실제 매출을 섞지 않는다. 자료가 없는 부분에 안전한 다음 확인 행동을 주되 지어내지 않는다.

기존 관광안내 3~5명·2~4주·자발적 재방문 1~2명 기준을 낮추지 않는다. 사용자 이름·회사·고객 정보는 공개 기록에서 제외한다. 구매 거절을 전체 시장 부재의 증명으로 삼지 않되, 고객을 만날 수 없으면 기능 개발로 대신하지 않는다.

가격은 저가 시험 범위를 가설로만 제안하고 수납·환불·지원 시간·변동비를 반영한다. 방문수나 구두 호감을 매출로 계산하지 않는다. 고객 데이터 연결이나 결제 시스템 개발을 첫 매출의 필수 전제로 만들지 않는다.

## 8. 경력 활용과 투자 판단

90일 끝에 남길 것은 실제 문제 정의·업무 개선·데이터 품질·원가·실패 복구·사용자 검증 사례다. 본인 판단·설계·검증과 AI 작성 부분을 구분한다. 리테일 영업운영/운영기획/데이터 활용/업무개선 관점에서 어느 역할에 어떤 증거가 유효한지 정리한다. 특정 합격·연봉·개발자 숙련도를 보장하지 않는다.

처음부터 이직 자료를 병행하고 3개월 뒤까지 지원을 미루지 않는다. 공개 가능한 자료만 쓰고 회사 내부자료·거래처 이해상충·개인정보는 별도 검토한다.

최초14일12시간, 총90일80시간은 제안 상한이다. 수행량 보장이 아니다. 이를 넘겨야 한다면 무엇을 버릴지 먼저 제시하라. 수익이 0일 때도 합리적인 계획인지, 실제로는 범위를 더 줄이는 것이 나은지 최종 판단하라.

## 9. 반드시 원하는 답변 형식

맨 위 ‘시간 없을 때 보는 결론’ 8~12줄. 그 아래 다음 내용을 대제목·중제목으로 정리한다.

1. 현재 구현/운영 확인/미확인/제안의 구분표와 실제 근거.
2. 이전 방향의 잘못된 전제·충돌·버려야 할 과제.
3. 정체성 한 문장, 첫 사용자·구매자·배포 채널, 첫 상품 한 개.
4. 기존 코드 중 재사용할 것과 진짜 부족한 연결. 각 과제의 업무효과·완료증거·중단조건.
5. 토큰 없는 감사·자동복구 허용표 및 감시자 자기시험.
6. AI 예외 인계 흐름, 공식 지원 한계, 계정에서 검증할 순서, 중복·과금·무한개발 차단.
7. 최초14일 실행 순서와 30/60/90일 계속/축소/전환/종료 기준. 고객 시험은 첫 주부터 병행.
8. 매출 0/작은 유료 반복/비용 회수의 보수적 시나리오. 모두 가정 표시, 순기여와 시간 별도.
9. 이직용으로 남길 측정자료와 지금 지원서에 써도 되는 사실/아직 쓰면 안 되는 주장.
10. 최종 판정: ‘조건부 3개월 가치 있음 / 2주 시험만 / 축소 후 경력용 / 중단’ 중 하나를 근거와 함께 선택.

검토만 한 것을 구현 완료로, GitHub 저장을 배포/자동화 활성화로 보고하지 않는다. 애매하면 추가 개발을 권하지 말고 무엇을 확인해야 결론이 바뀌는지 말하라.
