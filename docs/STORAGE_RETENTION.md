## 2. 숫자 표기 기준

| 표기 | 뜻 |
|---|---|
| 공식 계정 측정값 | Cloudflare 계정 API(`/d1/database/{id}`)가 돌려준 값 |
| 공식 쿼리 메타 | Cloudflare가 쿼리 응답에 붙여 준 값(`size_after`, `rows_read`) |
| 실측 | 이번 실행이 인덱스로 직접 센 값 |
| 실측 상한 | rowid 범위. 삭제된 행이 있으면 실제 행 수는 이보다 작음 |
| 실측 하한 | 수집기가 스스로 기록한 D1 사용량. 사이트 방문자 읽기는 빠져 있음 |
| 내부 추정 | 위 값에서 공식을 밝혀 계산한 값 |
| 확인 불가 | 권한이나 자료가 없어 읽지 못함. 이유를 함께 적음 |

- 쿼리 수를 읽은 행 수로 보지 않았습니다.
- 논리적으로 저장된 행 수를 과금되는 쓰기 행 수로 보지 않았습니다. 행 하나를 추가하면 테이블 1행에 인덱스 수만큼 쓰기가 더해집니다.

## 7. 가장 중요한 발견: 지우는 것도 쓰기 비용이다

- D1에서 행을 지우면 테이블 1행과 인덱스 행을 쓴 것으로 계산됩니다. 가장 큰 테이블들은 인덱스가 1~4개라서, 행 하나를 지우면 약 2~5행을 쓴 것이 됩니다.
- 14일 보관을 "오래된 행 삭제"로만 운영하면, 매일 새로 들어오는 약 7,400행만큼 매일 지워야 합니다(혼잡 예측·출국장 대기·기상 예보·업종별 맥락).
  - 이때 쓰기가 하루 약 3만 행 늘어납니다. 이태원을 포함한 수집기 쓰기(약 4.7만 행 추정)와 합치면 **무료 일일 쓰기 한도의 약 77%**(NOTICE 초과)입니다.
  - 이미 쌓인 14일 초과분 약 76,900행을 지우는 데에도 쓰기 약 31만 행이 듭니다.
- 그래서 화면이 최신 것만 읽는 세 테이블(혼잡 예측·기상 예보·출국장 대기)은 "쌓고 지우기"가 아니라 **처음부터 최신 발표본만 제자리에서 갱신하는 방식**으로 바꾸는 것이 저장과 쓰기를 함께 줄이는 방법입니다.
  - 이는 변한 값만 쓰는 방식으로, `docs/ENGINEERING_DIRECTION.md`의 방향과도 같습니다.
  - 예를 들어 혼잡 예측은 지역×목표시각 12행만 두고, 값이 바뀐 행만 고칩니다.
  - 이렇게 하면 저장 증가가 하루 약 3.7MB 줄어듭니다. 현재 추정 증가의 약 60%입니다.
  - 쓰기도 줄지만, 정확한 감소량은 발표본 사이에 값이 얼마나 자주 바뀌는지에 달려 있어 아직 **미확인**입니다.

- 공항 예상 승객(A5) 수집기가 하루 약 70,000행을 읽어, 수집기 읽기의 대부분을 차지합니다(9/27 실측 하한). 무료 한도의 1.4%라 급하지 않습니다.
- 기존 정리 쿼리 두 개(`collector_runs`, `seoul_context`)는 `EXPLAIN` 결과 표 전체를 훑습니다. 지금 비용은 작지만 표가 커질수록 늘어납니다. 제안 3·4와 함께 인덱스 경계 방식으로 고치면 됩니다.
- 요약 API는 캐시 미적중 1회에 5,853행을 읽습니다. 캐시는 60초(`stale-while-revalidate` 300초)입니다. 실제 하루 비캐시 요청 수는 공식 분석 권한이 없어 **미확인**입니다.

## 10. 소유자 확인이 필요한 것

1. **Cloudflare 대시보드 확인** (비밀키를 채팅에 붙이지 마세요): Workers & Pages → D1 → `retailpulse-korea-production` → Metrics에서 최근 일별 읽기·쓰기와 저장 크기 추이를 보면, 이 문서의 "확인 불가" 칸을 공식 값으로 바꿀 수 있습니다.
2. **보관 제안 1~5 승인 여부.** 1을 승인하면 새 표·수집기·요약 API 변경을 별도 PR로 만들고, 전환 확인 뒤에 2를 진행합니다.
